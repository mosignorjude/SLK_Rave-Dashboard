# Firestore security model

These rules are designed for the Spark architecture: Firebase Authentication plus direct web-client access to Cloud Firestore. There is no Admin SDK or trusted Cloud Functions backend in this version.

## Access boundaries

- Every active role requires a signed-in user with a verified email and an approved Firestore profile.
- The app listens to the signed-in user's profile so role or status changes clear privileged screens and cached ledgers. Firestore Rules remain the access boundary for every server request; the listener is a client-side cleanup measure. For immediate application access removal, suspend the user's Firestore profile in the app. Disabling a Firebase Authentication account or revoking refresh tokens separately is not checked against already-issued ID tokens by these Firestore Rules.
- A user may create only their own pending profile and username. The Master Admin role can be claimed only by the verified `carpentersfamily001@gmail.com` account while the bootstrap marker does not exist.
- Only Admins can approve accounts, change roles, configure tickets and budgets, and manage categories. Budget categories store a percentage and whole-Naira amount; the browser validates that their amounts do not exceed the budget total. The Master Admin profile and marker cannot be changed through the browser after bootstrap.
- The User Management page warns when it sees no other approved Admin profile. Maintain and test a separate backup Admin account. The backup can manage the workspace but cannot transfer the protected Master Admin identity. If the original Master Admin account cannot be recovered, use the project-owner emergency migration procedure in `README.md`; there is no browser recovery bypass.
- Verified Guests, Members, and Executives can read the same authorized finance ledgers and list all ticket sales. Guests cannot write. Only Admins and Executives can create or edit their own revenue and expense records. Only Admins can delete revenue or expense records. Expenses do not require Admin approval. Expense amount corrections retain the prior value in the record and append the old/new values to the immutable audit event. Members can create ticket sales; the tier price must still match the quote shown in the open sale form, totals must remain within the ₦1 trillion money limit, and the write must atomically match the inventory increment. Sales cannot be edited or deleted.
- Unauthenticated visitors have no Firestore reads or writes. Guest account creation permits only the fixed `guest` role, and verified email is required for finance reads. Guests can read authorized budgets and allocations; only Admins can create, update, or remove them.
- Activity entries are append-only. Rules bind `actorId` and the displayed actor name to the authenticated profile, restrict action names by role, and require each event to reference a matching state change in the same batch or transaction. Financial and ticket writes link to the exact event ID. Signup and user access writes link both profile documents to their event. Admin configuration writes require a fresh `settings/workspace` marker and matching `configuration.updated` event in the same batch or transaction. The UI renders fixed labels. Only Admins can read the audit collection.
- Finance edit events carry before/after values for changed fields, and delete events carry a pre-delete snapshot. The app constructs these from the Firestore document read inside the same transaction as the finance write.
- The final catch-all rule denies all unspecified reads and writes.

## Important limits

Firestore rules validate identity, role, shape, and ticket inventory consistency. They cannot safely perform all aggregate business checks that were previously in Cloud Functions, such as enforcing a budget cap against every expense row. Direct writes therefore rely on trusted, approved finance roles for revenue and expense entry. Client-side checks improve usability but are not security controls.

The Rules do not maintain a trusted aggregate count of Admin accounts, so the continuity warning is advisory and cannot prevent every path to an operational lockout. They also intentionally provide no Master Admin transfer path. Stronger server-enforced recovery or a minimum-Admin invariant needs a carefully designed trusted registry or backend; do not add a client-controlled recovery bypass.

### Spark audit-detail limits

This release keeps direct browser-to-Firestore writes and does not use a trusted server. The browser reads the current finance document in a transaction and generates the `changes` and `snapshot` fields from that read. Rules limit those maps to the app's finance-field allowlist. When an event includes amount or status before/after details, Rules compare them with the actual stored and post-write records. When a delete event includes a snapshot, Rules compare its title, amount, and status with the pre-delete document.

This is partial verification, not a tamper-proof audit source. To stay within Firestore Rules evaluation limits, other allowed field details are not individually compared with the ledger. The Rules also accept legacy-shaped events that omit `changes` or `snapshot`; the current app writes them, but a permitted finance writer using a direct client can omit or forge unchecked detail values when creating an otherwise permitted event. Append-only Rules prevent later edits to an event, but cannot prove every client-supplied detail was truthful at creation. Reason requirements, role checks, linked writes, and amount-correction old/new checks remain enforced independently.

Treat the rich audit details as an operational record for the current Spark-only deployment, not as forensic or legally authoritative evidence. Avoid placing secrets or personal data in these fields. Any future increase in validation should be emulator-tested against the Rules expression budget before release; the current checks deliberately verify the highest-value fields while preserving normal ledger writes.

The Activity Log supports Firestore-backed event-category, Nigeria-local date-range, exact actor UID, and resource-type filters with bounded live results and cursor-based loading of older matching events. The actor UID is debounced while typing and matches `actorId` exactly; resource type matches `targetType`. Arbitrary full-text search across actor names, reasons, descriptions, and resources is not included: Firestore does not provide that search over this collection without additional indexed tokens or reading the history in full. Existing legacy events with missing or invalid `createdAt` values cannot appear in timestamp-ordered filtered queries. `firestore.indexes.json` declares the composite index combinations for these filters; deploy and verify the index rollout before release. Only the Admin Activity Log query is authorized by Rules.

Admins can export the matching audit query to a browser-generated CSV. The export uses the same Firestore filters, includes the actor/resource/action, Nigeria-local timestamp, reason, allowlisted change/snapshot maps, and legacy amount fields, and escapes CSV formula-like text. It reads through Firestore in bounded 40-record pages and stops at 5,000 events or 8 MiB of event rows; any capped export is explicitly marked partial in the file and UI. This still consumes Firestore reads and client memory, so a very large history requires narrower filters. The paginated reads are not a single point-in-time snapshot: events added while the export runs may not be included, and ordered queries exclude legacy records without a valid `createdAt`. Export is not written back to the audit collection because it is a read-only download and the browser cannot reliably prove the user saved the file; no trusted export-service event is generated.

### Notification separation

The current application has no notification collection, notification UI, or notification read/delete path. Audit history is read directly from `activityLogs` by the Admin Activity Log and its CSV export; opening the Activity Log does not change audit records. The Rules deny unspecified collections and keep `activityLogs` append-only. If notifications are added later, they must use a separate collection and recipient-scoped Rules so reading or deleting a notification cannot change an audit event. Under this Spark-only client architecture, notification delivery must not be treated as authoritative evidence that an audit event was created or viewed.

### Legacy audit records and migration

The current UI and Rules remain backward-compatible with audit documents that predate `reason`, `changes`, `snapshot`, and the legacy amount-detail fields. Missing details are shown as absent; the UI does not synthesize before/after values or snapshots. Missing or malformed timestamps are shown as “Time unavailable” rather than being presented as a recent event. Timestamp-ordered timeline, filter, and export queries cannot return documents with a missing `createdAt`; invalidly typed timestamps may also sort or display unexpectedly. No production records were read for this review, and no schema migration or backfill is planned: rewriting old append-only events would alter history and cannot safely reconstruct unrecorded values. Existing history should be preserved as-is.

The selected budget policy is **warn only**. Paid expenses and Deposit amounts count as paid spending; Pending expenses and legacy Unpaid records count as commitments. The Budget page shows cash remaining plus available funds after commitments. Expense saves show an advisory when the projected event budget or category allocation is exceeded. These warnings do not block app writes and can be bypassed by direct Firestore writes; they are not financial authorization controls.

The subsequent Member ledger correction was Hosting-only; no Rules changed in that release. Current live Member/Guest UI checks are recorded in `REGRESSION_CHECKLIST.md`. ## Emulator test coverage and findings

Run `npm run emulator:rules` and then `npm run test:rules` in a second terminal. The test-only configuration uses the `demo-slk-rave-rules` project ID on port 18080; the tests seed and clear emulator data only.

The current tests confirm role-based ledger reads, denial of self-promotion, atomic ticket inventory updates, duplicate ticket retry idempotency, protection against concurrent overselling, stale quote rejection, owner-only ticket point reads, invalid quantity and tier rejection, and ticket total limits. They also confirm Admin-only budget writes, required audit events for financial, ticket, user-access, category, tier, budget, and allocation mutations, and append-only audit records. They also record these unresolved behaviors:

- The rules allow individually valid budget allocations whose combined amount or percentage exceeds the event budget. The browser checks these totals, but a direct Firestore write bypasses that check.
- Audit enforcement proves that a permitted write shares an atomic operation with a matching append-only event. Deletion events for expenses and revenues use the deleted record's document ID as the activity-log document ID because Firestore Rules cannot construct a dynamic ID from a prefix and target ID. Generated record IDs make collisions with existing random activity IDs extremely unlikely, but a collision would prevent deletion and require administrator review.
- Configuration changes share one event per transaction. The event is anchored to the `settings/workspace` marker, so budget edits can audit many allocation writes or deletes with one event rather than consuming Rules access calls per row.

The expense create/edit mismatch and audit actor/action-label spoofing have been restricted and covered by emulator tests. Mandatory logging is now enforced for the covered writes. Aggregate budget overruns remain unresolved because the selected policy is warn only.

The Task 18 security review found that Executives could delete their own financial records and approve their own expenses through direct Firestore calls, despite the intended role policy and Admin-only review controls. These permissions are now denied by Rules; the UI hides deletion controls from Executives. Emulator regressions verify Executive denial and Admin success for financial deletion and expense review.
